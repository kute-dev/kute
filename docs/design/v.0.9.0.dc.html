Jobs — attempts, not status

A Job that failed already told you everything, in five pods that no longer exist. Kute's job view is an attempt ledger — every pod the job ever made, its exit code, and its logs, kept reachable after the pod is gone. Two verbs earn keys: ctrl-r rerun (honest about Job immutability) and s suspend, shared with CronJobs (36c). Indexed jobs get one extra widget and no extra screen.

JOBS ↵ attempts l logs ctrl-r rerun s suspend y yaml ctrl-d delete ? help
  • SOURCE is the column that makes the list usable. A namespace's Jobs list is mostly hash-suffixed cronjob spawn you don't care about, mixed with the one standalone migration you do. Resolved from ownerRefs + helm hook annotations + kute's own manual tag (36b) — `o` groups by it, `/` filters to `standalone` in one keystroke.
  • FAILED counts pod attempts, not jobs — a job at `0/1` with `3` failed has burned its backoffLimit; a running job with `1` failed is retrying and probably fine. Two numbers that mean different things get two columns, never one "status" string.
  • DURATION runs live for active jobs and freezes at completion — and turns red when it hits activeDeadlineSeconds, which is how `migrate-schema-v42`'s exact `10m00s` reads as a deadline kill rather than a coincidence.
  • Suspended jobs (spec.suspend, 1.24+) use the same struck-through treatment as suspended cronjobs and stay in sort order. `s` toggles, same key, same asymmetric confirm as 36c.
  • `↵` opens the attempt ledger (37b), not a describe page. `l` tails the newest attempt's pod directly from the list — the common case is "show me why it failed", and that shouldn't cost two hops.

ATTEMPTS ↵ logs of this attempt d diff vs attempt 1 e events ctrl-r rerun esc back ? help
  • `(collected)` is the whole idea. By the time you look, the failed pods are garbage-collected and `kubectl logs` returns nothing. Kute watches Jobs continuously, so it captured each attempt's terminal state and tail as it happened — the ledger survives the pods. `↵` on a collected attempt opens the retained tail, clearly labelled as retained, never presented as live.
  • "Same failure all three times" is the read you actually want: if attempt 3 differs from attempt 1 it's flaky infra, if they're identical it's your code. Kute compares the retained tails and says which — `d` shows the diff when they differ.
  • The failure card promotes the deepest real message, same recipe as pod detail (spec 5a) and the cert chain (35a): not `BackoffLimitExceeded`, which tells you nothing, but the log line that preceded the exit.
  • ttlAfterFinished gets a countdown when it's set, in amber. "This evidence disappears in 12h" is operationally urgent and invisible everywhere else.
  • Attempts are Pods — `↵` into logs, exec, everything from spec 5a still applies for ones that still exist. No new pod machinery, just an index over them that outlives them.
37c ctrl-r — rerun, honest that Jobs can't be rerun it's a copy with a new name · kute says so instead of pretending
✕ migrate-schema-v42 0/1 10m00s 1 — standalone 2d
Jobs are immutable once created. "Rerun" means a new Job from the same pod template.
▸ create migrate-schema-v42-rerun-1 — same template, new name, old job and its ledger kept ○ replace migrate-schema-v42 — delete then recreate under the same name, ledger lost
↑↓ to choose · replace is the only option if something references the job by name
◷ it failed on the deadline activeDeadlineSeconds 600 · the last run used all of it rerunning unchanged will very likely do the same
will run kubectl create job migrate-schema-v42-rerun-1 --from=job/migrate-schema-v42 -n vna-stage ↵ create · y copy · esc cancel
JOBS rerun migrate-schema-v42? reversible · ctrl-y to edit the template first
  • Every other tool calls this "rerun" and quietly deletes your Job. Kute names the two real options and defaults to the non-destructive one — a suffixed copy, so the failed job and its attempt ledger (37b) survive for comparison. Replace exists because sometimes the name matters; it's the second choice, not the hidden behaviour.
  • The amber strip is diagnosis, not decoration. When the previous failure was a deadline kill or an image pull error, rerunning identical config is futile — kute says so and offers `ctrl-y` to edit the template on the way through. It only appears when the prior failure is one kute can classify.
  • Same `ctrl-r` as the CronJob run-now verb (36b) — both create a Job from a template, and the modifier consistently marks "this creates something".
  • Rerun on a cronjob-owned Job creates a standalone copy, not a new cronjob run, and the confirm says so: the copy won't count toward history limits and won't be garbage-collected with the schedule's set.
  • Reversible tier throughout — `↵`, no `y`. Replace escalates to danger tier (`y` + name on PROD) because it does delete.

INDEXED ↵ index attempts l logs of index 3 f failed only esc back non-indexed jobs show attempts as a flat list instead — 37b
  • `completedIndexes: 0-2,4-7` is a real API field and a genuinely hostile one to read. The map is that string, rendered — and the gap in it is the answer: index 3 is broken, the other eleven are fine.
  • Per-index duration turns the map into a skew detector. Uniform times mean good sharding; one index at 4× the mean means your partition function is wrong. Free, from data already on the pods.
  • Same screen as 37b — the map replaces the flat attempt list when `completionMode: Indexed`, everything below it is identical. One screen, two renderings, not two destinations.
  • Kute reads podFailurePolicy and says whether a failure counted — "no rule matches 137 · counts against backoffLimit 6" is the difference between a job that will recover and one that won't, and it is otherwise buried in spec.
  • ETA is honest arithmetic from observed index durations and parallelism, shown only once enough indexes have finished to mean anything. No progress bar; a fraction and a number.
