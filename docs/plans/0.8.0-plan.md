# Kute v0.8.0 CronJobs Implementation Plan

Target design: `docs/design/v.0.8.0.dc.html`, sections 36a-36e.

This plan replaces the older CronJob contract currently summarized in `docs/design/README.md:135-137`. It preserves the shared resource-list skeleton, lazy informer behavior, command registry, action controller, pure render paths, fake-provider parity, both themes, and the existing navigation stack.

## 1. Outcome

Deliver a CronJob experience that answers the operational questions directly:

1. The shared CronJobs list shows schedule, suspension state, active runs, last terminal outcome, and a live next-run countdown when the evaluation timezone is knowable.
2. `ctrl-r` stages a manual run with an overlap warning when appropriate, then creates a traceable standalone Job.
3. `s` suspends or resumes with asymmetric friction and truthful missed-schedule behavior.
4. `S` opens a pushed schedule editor with validation, timezone handling, next-five-run proof, and an old/new firing-set comparison.
5. `enter` opens a pushed CronJob detail screen with facts, the latest failure, and retained associated Jobs.

The implementation must not make Job or CronJob informers eager at connection time and must not poll Kubernetes to update countdowns.

## 2. Existing State and Required Replacement

| Area | Current implementation | v0.8.0 target |
|---|---|---|
| Registry | `internal/resources/registry.go` has basic CronJob columns | `NAME / SCHEDULE / SUSP / ACT / LAST RUN / NEXT` with CronJob-specific health semantics |
| Projection | `projectCronJob` only reads the CronJob and calls `time.Now()` | Cache-local CronJob + Job aggregation, optional Pod enrichment, caller-supplied clock |
| Enter | `openCronJobPods` jumps directly to filtered Pods | Push CronJob detail |
| Run now | Generic `TierInline` `y/N`, Unix timestamp name | Staged Enter action, conflict card, readable UTC `-manual-HHMM` name, source annotations |
| Suspend | Immediate `TierNone` both directions | Suspend: danger confirmation and PROD typed name; resume: staged Enter action |
| Schedule | Inline browse text buffer in `cronjobschedule.go` | Dedicated pushed task with schedule/timezone analysis and undo |
| Detail | None | New `tasks/cronjobdetail` task |
| Fake/demo | Two sparse CronJobs, no associated Jobs | Success, failure, active, suspended, manual, timezone, and unrelated-control fixtures |

## 3. Decisions and Truthful Deviations

These decisions are prerequisites because the HTML contains claims that current Kubernetes state cannot always prove or that conflict with repository invariants.

### 3.1 Canonical design text

Update `docs/design/README.md` section 36 to summarize 36a-36e and remove the old direct-to-Pods, immediate-suspend, and inline-schedule contracts. Add the new HTML anchors to the design-file inventory near the top of the README.

Do this in the first implementation change so code and tests do not knowingly target a design that the repository still calls incorrect.

### 3.2 Lifetime run total

Do not render `4 kept of 218 run` from inferred schedule occurrences. Kubernetes exposes retained Jobs and history limits, not the lifetime number of Jobs already garbage-collected.

Render truthful copy instead:

```text
4 retained · history limits 3 succeeded / 1 failed
```

If a future persisted Job ledger supplies an observed total, label it as observed-since rather than lifetime. No persisted-state schema change is required for v0.8.0.

### 3.3 Suspension duration and missed schedules

Kubernetes does not store when `spec.suspend` changed. Stamp Kute time and expected-generation annotations when Kute suspends a CronJob, and clear them when Kute resumes it. Trust the timestamp only while the annotated generation equals the current CronJob generation. This prevents an external resume followed by a later external suspend from reusing a stale timestamp. For CronJobs suspended externally, or changed in a way that invalidates the generation marker, show `suspended · start unknown` and omit a fabricated skipped count.

The HTML says missed runs are never backfilled. Kubernetes can create one immediate Job after unsuspension when missed schedules remain eligible, especially when `startingDeadlineSeconds` is unset. Replace the absolute claim with a computed warning:

```text
N schedules were missed · Kubernetes may start one immediately on resume
```

When the starting deadline makes every missed run ineligible, say so explicitly. Keep the count bounded and report `100+` when it exceeds the CronJob controller's practical missed-schedule threshold.

### 3.4 Manual Jobs and ownership

Keep manual Jobs ownerless so CronJob history GC does not delete them. Associate them with their source CronJob through Kute annotations, not a fake owner reference or name-prefix matching.

The detail heading should therefore read `associated with this cronjob`, not `owned by this cronjob`, because it includes both controller-owned scheduled Jobs and annotated standalone manual Jobs.

### 3.5 Failure evidence

Use retained API data only:

1. Job Failed/Complete conditions provide the stable reason and message.
2. `Job.Status.Failed` provides the failed-attempt count; existing owned Pods can add a representative termination reason, exit code, and logs target.
3. If Pods have already been collected, omit exit-code/log claims and retain the Job condition message.

Do not imply that Kute retained logs; that is v0.9.0 Job-ledger scope and no such store exists today.

### 3.6 Detail movement keys

Preserve the repository invariant `j/k == up/down`. In CronJob detail, `j/k` and arrows move through the Jobs table; `[` and `]` move between sibling CronJobs, matching `poddetail`.

This intentionally replaces the HTML keybar's `j/k next cronjob`, which conflicts with selecting Jobs for `enter` and with the global movement contract.

### 3.7 Job-detail dependency

Section 36e needs a destination for `enter` on an associated Job, but the v0.9.0 Job attempt-ledger task does not exist. For v0.8.0, emit the shared goto navigation for the exact Job (`GotoResourceMsg{Kind: KindJob, Namespace, Name}`), which pushes a Jobs browse view with the row selected. Do not build a partial bespoke attempt ledger inside CronJob detail.

When v0.9.0 lands, replace this seam with `OpenJobDetailFunc` without changing CronJob aggregation or table data.

### 3.8 API-server version and `spec.timeZone`

The repository currently has no API-server-version capability, and `CLAUDE.md` explicitly permits only two one-shot reads. The v0.8.0 editor can always display and validate a populated `spec.timeZone`, but it cannot truthfully render `cluster < 1.25` without a new read. Older servers may prune an unknown field rather than return a hard error, so writes must not rely on server rejection alone.

Recommended product gate before implementation:

1. Approve one cached `Discovery().ServerVersion()` read during connect/context switch.
2. Document it in `CLAUDE.md` and `docs/lazy-informers.md` as a third one-shot read, never a poll.
3. Store a tri-state `supported / unsupported / unknown` capability on the stable cluster/fake context and inject a package-local capability interface into the schedule task.
4. Treat an already-populated `spec.timeZone` as direct evidence that this object supports the field.
5. Treat Kubernetes 1.27+ as supported, below 1.25 as unsupported, and 1.25-1.26 as unknown unless stronger evidence exists because the beta feature gate could be disabled.

If that gate is not approved, omit version-specific copy and disable timezone writes when capability is unknown; existing populated values remain visible. Do not infer API-server support from Node kubelet versions and do not risk a successful response that silently prunes the field.

### 3.9 Unset timezone and NEXT

When `spec.timeZone` is unset, Kubernetes evaluates the schedule in the kube-controller-manager process's local timezone. Kute cannot discover that timezone from the CronJob or current interfaces.

Compute an exact NEXT only when `spec.timeZone` is explicit. For an unset timezone, render `controller local` and `NEXT —` with an explanatory detail/hint instead of using the workstation timezone or assuming UTC. The schedule editor should encourage selecting an explicit timezone when the capability is supported.

## 4. Target Architecture

### 4.1 Cache-local aggregation

Add `internal/resources/cronjobs.go` with pure aggregation and projection helpers. Proposed public data shapes:

```go
type JobSource int

const (
    JobSourceScheduled JobSource = iota
    JobSourceManual
)

type JobSummary struct {
    Namespace      string
    Name           string
    UID            types.UID
    Source         JobSource
    Creator        string
    ScheduledAt    time.Time
    StartedAt      time.Time
    CompletedAt    time.Time
    Active         bool
    Succeeded      bool
    Failed         bool
    Completions    string
    FailedAttempts int32
    Reason         string
    Message        string
    ExitCode       *int32
    PodName        string
}

type CronJobSummary struct {
    Object       *batchv1.CronJob // deep-copied snapshot
    Runs         []JobSummary
    LastTerminal *JobSummary
    ActiveRuns   []JobSummary
    SuspendedAt  *time.Time
}
```

Exact names may change during implementation, but retain these responsibilities:

1. Build all summaries once per list/detail load from slices already read from informer caches.
2. Keep absolute timestamps and cron/timezone data in model state.
3. Produce display strings from a supplied `now`; never read the clock in render code.
4. Share Job association, source, outcome, duration, and failure derivation between browse and detail.

Add helpers with testable inputs:

```go
BuildCronJobSummaries(cronJobs, jobs, pods []runtime.Object) []CronJobSummary
ProjectCronJob(summary CronJobSummary, now time.Time) Row
ProjectAssociatedJob(summary JobSummary, now time.Time, columns JobColumns) Row
NextCronRuns(schedule, timezone string, from time.Time, count int) ([]time.Time, error)
CountCronRuns(schedule, timezone string, from, to time.Time, limit int) (count int, truncated bool, err error)
```

### 4.2 Association rules

Associate a Job with a CronJob only when one of these rules succeeds:

1. A controller owner reference has `Kind == kube.KindCronJob.APIKind()` and UID matches the CronJob UID.
2. A manual Job has Kute source-name and source-UID annotations matching that CronJob.

Use kind/name fallback only for sparse fake objects whose UID is absent on both sides. Reject same-name/different-UID owners so delete/recreate does not inherit stale history. Never associate by name prefix.

Add annotation constants in `internal/kube`, for example:

```text
kute.dev/cronjob-name
kute.dev/cronjob-uid
kute.dev/triggered-by
kute.dev/triggered-at
kute.dev/suspended-at
kute.dev/suspended-generation
```

Keep `cronjob.kubernetes.io/instantiate=manual` for compatibility with kubectl conventions.

### 4.3 Last-run and glyph semantics

`LAST RUN` means the newest terminal associated Job, not the currently active Job. This allows an active CronJob row to say `2m ago check` while `ACT` says `1`, as shown in 36a.

Derive visual state in this priority order:

1. Suspended: pause glyph, dim/strike name, amber `yes`, no NEXT.
2. Active: active glyph and amber ACT count.
3. Last terminal failed: failed glyph and failed LAST RUN.
4. Last terminal succeeded: running/healthy glyph and successful LAST RUN.
5. No retained history: neutral glyph and `no retained runs` without claiming the CronJob never ran.

Store active/suspended as cross-cutting row facts. Extend `resources.HealthCounts` with exclusive display extras such as `Active` and `Suspended`, following the existing `Outdated`/`ExpiringSoon` pattern. CronJob health should report:

1. OK: last terminal run succeeded.
2. Fail: last terminal run failed.
3. Neutral: no retained terminal run.
4. Active: cross-cutting count, even when the previous terminal run succeeded.
5. Suspended: cross-cutting count, even when history exists.

This matches the HTML, whose segments can sum to more than the CronJob count.

### 4.4 Lazy loading and readiness

Opening CronJobs may start exactly these lazy caches:

1. `KindCronJob`, because it is the selected list.
2. `KindJob`, because last outcome, active runs, and history are visible.

Pods are already eager at connect and may be read best-effort for exit/log targeting. Do not add Job or CronJob to `eagerKinds`.

Add `KindCronJob: {KindJob, KindPod}` to `internal/tui/tasks/browse/auxkinds.go` so Job/Pod changes reload the list. Treat only CronJob and Job as required for initial readiness; Pod data enriches but does not block.

Before entering Ready or Empty for CronJobs:

1. Check `tui.KindsSynced(lister, KindCronJob, KindJob)` even when CronJob rows are already present.
2. Schedule the existing 250 ms cache-sync retry when either required cache is not settled.
3. Check `tui.KindsError` immediately after the sync gate.
4. Never render `no history` while the Job cache is still filling.
5. If the Job cache settles with an error, keep already-loaded CronJob schedule rows visible, render history cells as unavailable, and show an inline load-error strip; do not silently claim no runs.
6. Carry an explicit aggregation-complete flag. While Job data is unavailable, block run-now/suspend preflights that depend on active-run knowledge, or show a mandatory `overlap unknown` warning; never treat a failed Job read as evidence that no run is active.

Do not introduce a `ListCronJobRuns` optional lister seam. Existing `ListRaw` calls keep the join cache-local and avoid another decorator-forwarding failure mode.

### 4.5 UI-only clock

Use a one-second `tea.Tick` only while a CronJob list/detail/schedule screen is active. The tick updates model `now`, rebuilds time-derived cells from stored summaries, preserves selection/filter/marks, and schedules the next tick.

The clock tick must never call `ListRaw`, metrics, discovery, or any API. Resource changes remain watch-driven and use the existing debounce.
