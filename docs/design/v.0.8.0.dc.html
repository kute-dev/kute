CronJobs — the schedule is the thing you operate

A CronJob's three questions are: did the last run pass, when is the next one, and is it even enabled. Kute answers all three in the list. Three verbs earn keys — ctrl-r run now, s suspend/resume, S edit schedule — and nothing else gets chrome. Jobs and Pods stay generic lists reached by ↵.

CRONJOBS ↵ jobs ctrl-r run now s suspend S schedule l logs y yaml ? help
  • NEXT is computed, not stored — Kute parses the cron expression against spec.timeZone and counts down live off the same clock as the age column. kubectl can't show it; it's the single most-asked question about a cronjob.
  • LAST RUN carries its outcome inline (✓/✕) from the newest owned Job — so the list answers "is this thing healthy" without a detail hop. The failure card in the panel promotes the deepest message verbatim, same move as pod detail (spec 5a) and the cert chain (35a).
  • Suspended rows stay in name order — struck-through, dimmed, amber `yes` in SUSP, NEXT reads `—`. They don't sink to the bottom: a suspended cronjob is usually suspended by you, this morning, and you need to find it where you left it.
  • The right panel is the marked row's last 5 runs — history from ownerRefs over the Jobs watch, no extra request. Below it the metadata that changes behaviour: concurrency policy, deadline, history limits, timezone, backoff. Nothing decorative.
  • `↵` opens the generic Jobs list filtered to this cronjob; `l` tails logs of the newest run's pod (spec 3a plumbing). No CronJob detail screen — Jobs and Pods already have theirs.

after ↵ — the manual run appears in history, tagged

▲sync-inventory-manual-1402manual · you4snow
CRONJOBS ✓ job created · sync-inventory-manual-1402 l tail its logs · ↵ open jobs
  • The whole reason run-now needs a confirm step isn't danger, it's the overlap nobody expects: `--from=cronjob` ignores concurrencyPolicy entirely. Kute says so, names the running job, and lets you proceed. Warning card only appears when there's an actual conflict — otherwise it's just the will-run line.
  • ctrl-r, not r, because `r` is restart/renew everywhere else in kute and creating a job is not a restart. The modifier marks it as a create, matching ctrl-d for delete.
  • The generated name is deterministic and readable — `-manual-HHMM` — so it's obvious in history, in logs, and to whoever finds it tomorrow. Manual runs carry a `manual · you` tag in the history panel, sourced from the creating annotation.
  • Reversible tier: it doesn't touch the schedule, and the job is deletable. So — inline line, no modal, no `y` to confirm. Friction scales with risk; compare 36c.
36c s — suspend and resume, one key both directions suspend is danger tier (`y` to confirm) · resume is reversible
suspending an enabled cronjob — silence has consequences, so it costs a keystroke
● backup-postgres 0 2 * * * no 0 12h ago ✓ in 11h58m
⏸ suspend backup-postgres nothing will announce this later
The 02:00 run stops happening. Missed runs are not backfilled on resume — every night it stays suspended is a backup that never exists.
running jobs are unaffected · no active jobs right now
will run kubectl patch cronjob/backup-postgres -n vna-stage -p '{"spec":{"suspend":true}}' y suspend · esc cancel
DANGER press y to confirm PROD context would also require typing the name
resuming a suspended one — the same key, no confirm, and it tells you what you didn't get
⏸ warm-cache */5 * * * * yes 0 3d ago ✓ —
will run kubectl patch cronjob/warm-cache -n vna-stage -p '{"spec":{"suspend":false}}' ↵ resume · esc cancel
CRONJOBS resume warm-cache? suspended 3d · 864 runs skipped, none backfilled · next in 2m11s reversible · s again to suspend
  • One key, both directions — the row already tells you which way it goes (SUSP column, strike-through), so a second key would be redundant state to remember. The keybar label flips to `resume` when the marked row is suspended.
  • Asymmetric friction, deliberately. Suspend is the dangerous half: it fails silently and forever, and nobody gets paged for a backup that didn't start. So it's danger tier — `y`, plus name-typing on a PROD context (spec 20a's escalation). Resume can only cause work to happen, so it's `↵`.
  • Both directions state the backfill truth: Kubernetes does not catch up missed runs. Resume shows how many were skipped — computed from the cron expression across the suspension window — because that number is what tells you whether to also fire a manual run (36b).
  • Suspend doesn't kill in-flight jobs; the card says so, and names them when there are any. Kute never implies a stronger effect than the patch actually has.
  • Works on a marked set too — `s` over 4 marked cronjobs suspends all four behind one confirm, listing the names (spec 20a bulk kit).

will run kubectl patch cronjob/report-nightly -n vna-stage -p '{"spec":{"schedule":"30 1 * * 1-5"}}' ↵ apply · y copy · esc cancel
SCHEDULE tab timezone ctrl-y full yaml edit esc back reversible · was 30 1 * * * · esc after apply offers undo
  • Editing a schedule through YAML (spec 17a) works but is the wrong tool: cron expressions are write-only for most people. `S` gives one field and three kinds of feedback — per-field decoding, an English sentence, and the next five real timestamps. The timestamps are the proof; the sentence is a courtesy.
  • WHAT CHANGES is the part other tools skip. A diff of the old and new firing sets, in plain terms: what stops happening, how many runs a year, whether the pending run moves. Silently dropping weekends is exactly the mistake this prevents.
  • Timezone is shown always, editable on `tab`, and Kute states whether the cluster is new enough for spec.timeZone — on older clusters the field is disabled and reads `UTC (cluster < 1.25)` rather than letting you set something that silently does nothing.
  • Capital S, not a second modifier: shift-pairing keeps schedule next to suspend in muscle memory, and edits are rarer than toggles, so they get the harder key.
  • Reversible tier — a schedule patch changes nothing that already ran, and the old value stays offered as an undo. `ctrl-y` escapes to the full YAML editor for anything else on the object (concurrency, deadlines, history limits): one dedicated field for the thing you edit weekly, the generic editor for the rest.
